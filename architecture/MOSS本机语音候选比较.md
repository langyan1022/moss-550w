## 公开测速的口径

1. **gsv.cpp。** 作者在 Windows 10、Xeon E5-2675 v3 和 RTX 2070 8 GiB 上，使用同一参考、种子和中文短句。热机生成约 3.4 秒音频，V5 Turbo 的 ggml FP16 与 AR Q8 各用 945 和 1,028 毫秒，PyTorch 参考为 3,142 毫秒。这里计入整段生成。流式接口的 13 毫秒读数是 WAV 头。 [作者性能记录](https://github.com/KakaruHayate/gsv.cpp/blob/f83f0ef5f665d07d90c0c455060b96e69e851596/docs/benchmark.md)
2. **Breeze TTS 2。** 原作者在已预热的 H100 快速路径测得首音频低于 40 毫秒。社区 C++ 项目另有 RTX 3060 12 GB 上的 Vulkan 对照。在 Q8、有语气控制时，速度约为实时的 1.58 倍。其实验机有自定义 Tensor Core 设置。 [官方条件](https://github.com/breezeblue-ai/breeze-tts) · [社区 Vulkan 测试](https://github.com/HoppouAI/Breeze-TTS-2.cpp#performance)
3. **VoxCPM2 与 IndexTTS 2.5。** 官方列出的 RTX 4090 实时率分别约为 0.30 和 0.21，均用生成时间除以音频时长。两组文本、参考音色和启动条件有差别。 [VoxCPM2 版本比较](https://github.com/OpenBMB/VoxCPM#-models--versions) · [IndexTTS 性能记录](https://github.com/index-tts/index-tts#-inference-speed)
4. **AnifLive-TTS 1.5。** 作者在 RTX 5070 Ti 上固定输入和参数，预热后复用 HTTP 连接。v5Turbo 的首个有效音频 P50 为 80.93 毫秒，P95 为 84.33 毫秒。同一来源的 gsv.cpp Vulkan 探索性测试 P50 为 354.45 毫秒，三组会话。读数从 HTTP 请求到达到门限的音频数据，不含扬声器输出。 [正式发布说明](https://github.com/Hiruynk/AnifLive-TTS/blob/f5fc72f4a380f6ae3d94628a84402c034cc837ce/RELEASE_NOTES_v1.5.0.md) · [作者性能记录](https://github.com/Hiruynk/AnifLive-TTS/blob/f5fc72f4a380f6ae3d94628a84402c034cc837ce/benchmarks/V1_5_BENCHMARK_SUMMARY.json)

2. **日常 OmniVoice，RTX 3070 Ti Laptop。** 同一篇散文从点击发送到 Edge 音频时钟首个有效采样为 25.79 秒。首段 HTTP 等待含传输约 25.30 秒，两组后台批量合成分别用时 4.01 秒和 3.64 秒。五段播完，四处 Web Audio 调度空档均小于 10 毫秒，声音本身的段间静音为 0.80–0.98 秒。首次采样仅记录到 Windows 虚拟环境启动器的工作集，内存监视改为递归跟踪实际解释器后需复测。Edge 运行静音，全程未测实体扬声器。`浏览器验收` · [Web Audio 时钟定义](https://www.w3.org/TR/webaudio/#dom-audiocontext-getoutputtimestamp)
3. **音色参照。** 已登记的影片原声中有 2.54 秒台词与主参考互不重叠，逐采样核对确认来自同一条 16.60 秒母带。另两条旧录音只有内容、时长和哈希，缺少说话者与采集来源。目前有同源不同台词可供试听，跨来源的还原度仍待核实。

## OmniVoice 两次播报之间的内存和延迟

用同一条文件麦克风报时录音，两组 ABBA 各测四个新 CUDA 进程，分别尝试在权重加载时和权重加载后并行导入空间混音模块。两组音频摘要各自完全一致。前一种把合成后等待混音的中位数从 798 毫秒降到 27 毫秒，同时增加了约 0.71 秒的检查点读取时间，首声中位都约 12.17 秒。后一种把混音等候从 830 毫秒降到 25 毫秒，生成阶段中位约增加 0.50 秒，提交到首声的中位从 11.77 秒变为 11.92 秒。日常采用原串行流程。下一步测模型装载前是否有可独立提前完成的工作。`与权重并行对照` · `权重到位后的对照`

采用新进程预导入进行隔离 HTTP 验收。旧推理进程确实退出，新的 Python 进程在待机时未进入 GPU 计算进程列表。下一句复用待机进程，随后再冷却。固定短句的磁盘 WAV 请求不延长待机，超时后该进程退出。该次验收用环境变量启用候选。`HTTP 验收` · [PyTorch 显存计量](https://docs.pytorch.org/docs/2.15/notes/cuda.html#memory-management)

静音 Edge 用同一条真实电量和系统音量查询交错测了四轮。两边都给输入预导入 4 秒，先用另一句动态语音合成建立进程，再等该进程退出。将测试的空闲回收缩至 10 秒，保留 90 秒待机窗口。浏览器有效 PCM 首声中位数由 10.29 秒降到 8.26 秒，四轮 WAV 逐字节一致，目标请求均由 CUDA 生成。待机工作集约 573 MiB，私有提交约 2.13 GiB，GPU 计算进程中未发现待机 PID。最后一次实测待机进程在 89.98 秒退出。日常实例采用 150 秒回收和 90 秒待机窗口，启动前两项可用内存各须 11 GiB，等待期间每 5 秒复查，任一项低于 8 GiB 时回收。`浏览器与进程实测` · `压力与并发回归`

同一句在 Intel Iris Xe 上用 audio.cpp Vulkan 直接生成，冷请求首个有效 PCM 为 27.15 秒，热请求为 13.72 秒，二者输出的 5.28 秒干声 WAV 字节一致，SenseVoice 转写汉字全部匹配。峰值进程工作集 6,671 MiB。该测量使用同一参考、同一权重及十六步推理，未应用 MOSS 空间混音。`Intel Vulkan 计时` · `转写核对` · `原生干声`

## 本机复验用例

1. 固定六秒 MOSS 原参考、文本和种子。短文本用日常回应和带日期、负温度的天气句。长文本用两首唐诗、三段约两百字的散文。测试同一句的两种语气，并试听叹气、笑声与字句的连接。对照项包括重音、语速、节奏、吞字和误读。
2. 保留原始干声，并用目前的 MOSS 空间混音分别生成对应版本。记录同响度条件下的左右声道关系、峰值、尾音和混音增量耗时。音色相似度用本地说话人向量与试听对照。现有 `reference-warm.wav` 属于原参考的子段，独立原声需要另外找到。
3. 逐引擎用新进程计时，分别记录连接到响应头、首个达到 -45 dBFS 的 10 毫秒 PCM 帧、整段完成和浏览器实际开播。测试热重复、长文续播、丢包、停顿、打断后的下一轮。记录峰值系统内存、显存、CPU 用时和离开后回收。
4. GPU 语音、本机语音识别与浏览器性能用例通过同一个硬件测试启动脚本串行运行。锁覆盖子命令执行的全程，命令结束后释放，根据用例所需内存检查启动条件。内存不足的中止记录保留，归档的试听片段标明其对应冷启动或热请求。实测第二个测试进程被拒绝，释放后 Vulkan 枚举正常。 [独占启动脚本](../run-hardware-benchmark.ps1) · `本机验收回执`

## 可以复用的实现思路

- 参考 AnifLive-TTS 的能力查询、整段及分句表达、同会话追加文字和取消。MOSS 保留现有播报轮次，继续用同一播放器控制字幕和频谱。流式引擎通过本机 PCM 接口接入，并按到达时间核对播放空档。 [AnifLive-TTS API](https://github.com/Hiruynk/AnifLive-TTS/blob/f5fc72f4a380f6ae3d94628a84402c034cc837ce/docs/API_EN.md)
- Vulkan 设备枚举和单进程模型复用可直接由 audio.cpp 或 gsv.cpp 提供。日常语音入口继续做文本规范化，分句和语气由 MOSS 的会话状态传下去。优先实测有真实增量输出的 VoxCPM2 与 Breeze TTS 2。
